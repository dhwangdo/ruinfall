# Ruinfall Godot 포팅 목적과 진행 계획

작성일: 2026년 11월 12일, 한국 시간 기준

실제 작업과 완료 판정은 [Godot 포팅 작업 체크리스트](GODOT_PORT_CHECKLIST.md)를 따른다.

## 현재 판단

**Godot으로 개발 기반을 옮기는 목적은 분명해졌다. 현재 작업물을 보존하고, 실제 플레이로 완성 여부를 확인할 수 있도록 작업 방식을 재정비한다.** 사용자는 PC 실행 파일만 얻으려는 것이 아니라, 앞으로 Ruinfall을 게임 엔진에서 개발하고 싶다고 설명했다. 브라우저마다 환경과 설정이 달라지는 경험, 게임 동작을 웹 기술로 직접 구현하는 데 드는 부담을 줄이고 싶은 것이다.

따라서 Godot을 선택한 것 자체를 잘못으로 볼 근거는 없다. 다만 엔진을 바꾼다는 결정과 현재 이식 작업이 효율적으로 진행된다는 판단은 별개다. 현재 포트는 기존 게임의 규칙과 화면을 GDScript와 Godot UI로 다시 만드는 규모이므로, 작성한 코드의 양보다 실제 플레이가 어디까지 일치하는지로 진행을 관리해야 한다.

처음부터 아무 계획도 없었던 것은 아니다. 초기 대화에는 작은 전투 하나를 먼저 완성하고 결과를 보고 전체 포팅을 결정하자는 제안이 있었다. 그러나 이후 전체 포팅으로 범위가 커졌고, 그 작은 결과물의 합격 여부를 판단하는 단계가 실제 진행을 통제하지 못했다.

사용자는 Luna에 맡긴 작업이 약 40시간 이어졌다고 설명했다. 이 시간만으로 모델의 능력이나 전체 작업의 가치를 판정할 수는 없다. 다만 실제 플레이의 합격 여부와 남은 작업을 명확히 관리하지 않은 채 원본과의 차이를 계속 찾아 고치는 방식은 재검토가 필요하다. 이후 사용자가 실제 작업 재개와 작업본·언어 결정을 요청해 Sol이 첫 실행 구간에 착수했다. 현재 판정은 체크리스트의 실행 기록을 따른다.

## 작업본과 구현 언어 결정

**2026년 11월 12일 결정: 현재 Godot 작업본을 활용하고 GDScript를 유지한다.** 원본 웹 게임과 포트의 현재 파일을 보관한 뒤, 확인한 결함을 고치며 검증한다. 처음부터 새 프로젝트를 만들거나 현재 GDScript를 C#으로 일괄 재작성하지 않는다.

이 결정은 이미 쓴 시간이 아까워서만 내린 것이 아니다. 현재 포트에는 지도·카드·전투·덱·서비스가 나뉘어 구현되어 있고, 첫 검사에서 드러난 시작 실패는 들여쓰기·타입 추론·변수 범위 등 구체적인 오류였다. 이 오류들을 고친 현재 소스가 지도와 전투 화면을 실제로 그리는 것까지 확인했다. 지금 확인한 문제에는 해당 부분을 수정하고 재검증하는 방법이 있다.

| 선택 | 현재 프로젝트에서의 판단 |
|---|---|
| 현재 작업본과 GDScript | 기존 규칙·자산·UI를 활용하면서 결함을 고치고 화면별 책임을 정리할 수 있다. 현재 선택이다. |
| 현재 작업본을 C#으로 전환 | C#의 정적 타입과 .NET 라이브러리·도구를 활용할 수 있다. 그러나 현재 GDScript 모듈을 옮기고 화면·규칙을 다시 검증하는 비용이 추가된다. 이를 필요로 하는 구체적인 팀·라이브러리 요구는 정해지지 않았다. |
| 새 프로젝트로 재작성 | 현재 작업본이 부분 수정으로 유지할 수 없는지 확인한 뒤에야 검토할 선택이다. 첫 실행 검사에서는 전체 재작성의 필요를 뒷받침하는 근거가 나오지 않았다. |

GDScript도 타입 주석과 정적 검사를 지원하며 Godot 편집기와 통합되어 있다. C#은 .NET용 Godot 편집기가 필요하고 .NET 생태계를 사용할 때 장점이 있다. 언어별 성능 차이는 계산 내용에 따라 다르므로, Ruinfall에서 측정하지 않은 성능 향상을 전환 근거로 삼지 않는다. [Godot 언어 안내](https://docs.godotengine.org/en/stable/getting_started/step_by_step/scripting_languages.html), [Godot C# 안내](https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/index.html)

GDScript를 유지한다는 것은 현재 구조를 그대로 고정한다는 뜻이 아니다. 실제 수정하는 경로부터 타입을 명확히 하고, 화면·입력·규칙·상태의 책임을 나누며, 실행 전에 스크립트 검사와 관련 기능 검증을 한다. 이후 C#으로 유지보수할 팀이 정해지거나 필요한 .NET 라이브러리가 생기거나 측정한 병목이 드러나면, 그 구체적인 범위에서 선택을 재검토한다.

## 처음 Godot을 요청한 이유

11월 10일의 「코드 변경」 채팅에서 확인되는 출발점은 두 가지다.

- 사용자는 “내 친구 준영이가 이 게임을 고도 엔진으로 포팅하는 게 좋을 것 같대”라며 가능성, 기간, 필요한 도움을 물었다.
- 이어서 “브라우저 전용이 아니었으면 해”라고 목적을 설명했다.

11월 12일의 추가 설명으로 이 목적이 구체화되었다. 사용자는 “게임을 만들 거면 게임 엔진이 더 나을 것 같다”, 브라우저마다 설정이 달라 문제가 생기며 웹 기술에서 게임 동작을 직접 구현하는 부담이 커 보인다고 설명했다. **목표는 별도 창을 만드는 데 그치지 않고, 앞으로 게임 엔진을 주 개발 기반으로 쓰는 것**이다. 초기 표현을 PC 실행 파일의 필요로만 해석하면 이 의도를 충분히 담지 못한다.

이 저장소에는 이미 Electron 실행기가 있다. [실행기 안내](../desktop/README.md)에 따르면 게임 실행에 인터넷, Node.js, localhost 개발 서버가 필요하지 않으며, 기존 웹 게임을 별도 데스크톱 창에서 실행한다. Electron 자체도 웹 기술을 데스크톱 앱으로 배포하기 위한 프레임워크다. [Electron 공식 소개](https://www.electronjs.org/docs/latest/)

Electron 실행기의 존재는 PC 배포가 이미 가능하다는 근거다. 그러나 사용자가 원하는 게임 엔진 중심의 개발 방식까지 대신하지는 않는다. 다음 구분은 Godot 선택을 다시 묻기 위한 조건이 아니라, 전환으로 얻으려는 효과를 분명히 하기 위한 것이다.

| 원하는 결과 | 판단 |
|---|---|
| 브라우저를 직접 열지 않고 PC에서 실행 | 기존 Electron 실행기로 충족할 수 있다. Godot 이식이 필수는 아니다. |
| 사용자별 브라우저 환경 차이를 줄이기 | Chromium을 포함하는 Electron 배포로도 사용자의 브라우저 선택에 따른 차이를 줄일 수 있다. 모든 PC의 표시·입력 차이가 없어지는 것은 아니다. |
| Chromium 같은 웹 실행 기반 자체를 제거 | Electron은 이 요구를 충족하지 않는다. Godot 같은 별도 실행 기반을 검토할 이유가 생긴다. |
| 앞으로 게임 엔진을 중심으로 화면과 연출을 개발 | 사용자가 밝힌 방향이다. Godot의 제작 도구와 재사용 가능한 화면 구조를 활용하는 것이 이식의 목적에 포함된다. |
| 성능이나 배포 문제 해결 | 현재 문제를 측정하고 작은 Godot 시제품으로 개선 여부를 확인해야 한다. 엔진 변경만으로 개선을 보장하지 않는다. |

Godot은 2D·3D 제작 도구와 여러 플랫폼용 내보내기 기능을 제공한다. 앞으로 게임 개발을 계속할 기반으로 이를 선택하는 것은 합리적인 방향이다. 전환 효과를 얻으려면 기존 화면을 다시 그리는 것과 함께, 이후 화면과 연출을 수정하기 쉬운 구조도 만들어야 한다. 브라우저 관련 문제나 구현 부담이 자동으로 전부 사라진다는 뜻은 아니다. [Godot 공식 소개](https://docs.godotengine.org/en/stable/about/introduction.html)

## 현재 작업물에서 확인한 상태

### 이미 상당한 구현이 있다

[Godot README](../godot/README.md)에는 지도 탐험, 전투, 보상, 덱 편집, 스티커 서비스, 저장과 복원까지 연결한 내용이 기록되어 있다. 지도와 전투 규칙, 카드·적 데이터, 입력과 화면 부품도 별도 GDScript 파일들에 존재한다. 40시간을 전부 무의미한 작업으로 보는 것은 맞지 않는다.

다만 README의 구현 목록, 카드 개수 일치, 일부 시드의 지도 비교가 곧 전체 플레이 동작의 일치를 뜻하지는 않는다. README에도 카드 효과와 예외 규칙의 추가 대조가 남아 있다고 적혀 있다.

### 중심 파일에 책임이 많이 모였다

검토 시점의 [main.gd](../godot/scripts/main.gd)는 5,631행이고, [battle_rules.gd](../godot/scripts/battle_rules.gd)는 2,297행이다. `main.gd`는 탐험·전투 상태, 저장 경로, 여러 화면과 입력 상태를 함께 소유한다. [main.tscn](../godot/scenes/main.tscn)은 이 스크립트를 연결한 단일 루트 Control 장면이다.

파일 길이만으로 잘못된 코드를 판정할 수는 없다. 그러나 현재 구조에서는 화면을 고치다가 시작 화면 전체가 로드되지 않는 식의 영향을 추적하기 어려워질 수 있다. 재개한다면 문제가 잦은 화면부터 책임을 나누되, 지금 당장 전체 구조를 다시 만드는 작업으로 확대해서는 안 된다.

### 실행 확인과 플레이 확인이 혼재했다

작업 기록에는 프로세스 응답, 창 핸들, 헤드리스 실행 성공을 확인한 보고가 여러 번 있다. 헤드리스 실행은 화면 없이 프로그램이 시작되는지 확인하는 검사다. 화면이 제대로 보이는지, 카드가 올바른 위치로 드래그되는지, 전투가 끝나고 보상이 지급되는지까지 증명하지 않는다.

실제로 최근 기록에는 존재하지 않는 `_refresh_battle_hand_actions()` 호출 때문에 `main.gd`가 로드되지 않아 회색 화면이 발생했고 이를 수정했다는 보고가 있다. 오래된 실행창과 최신 소스 실행을 혼동한 문제도 있었다. 이후 사용자는 정상 실행을 확인했지만, 이것이 전체 플레이 검증의 완료를 의미하지는 않는다.

[package.json](../package.json)의 `npm test`는 웹 빌드와 TypeScript 규칙·렌더링 검사를 실행하며 Godot 실행 검사는 포함하지 않는다. 기존 웹 테스트가 통과해도 GDScript로 옮긴 규칙이 자동으로 검증되는 구조는 아니다.

## 오래 걸린 이유에 대한 판단

**첫째, 작업 자체가 전체 재작성에 가까웠다.** React·CSS 화면을 Godot UI로 그대로 옮길 수 없으므로 카드 배치, 드래그, 툴팁, 스크롤, 애니메이션을 다시 구현해야 한다. 현재 선택한 GDScript 경로에서는 TypeScript 규칙도 별도로 옮겨 대조한다. Godot의 공식 지원 언어와 현재 프로젝트의 실행 방식이 기존 웹 코드와 다르기 때문이다. [Godot 스크립트 언어 안내](https://docs.godotengine.org/en/stable/getting_started/step_by_step/scripting_languages.html)

**둘째, 제품 목표를 구현과 검증 항목으로 충분히 나누지 않았다.** “현재 브라우저 버전이 Godot에서 똑같이 잘 돌아간다”는 사용자 목표는 타당하다. 이를 화면, 조작, 규칙, 저장, 배포의 확인 항목으로 바꾸는 것은 구현을 맡은 AI의 역할이다. 동작 예외, UI 치수, 툴팁, 작은 연출을 그때그때 찾아 고치기만 하면 끝을 판정하기 어렵다. 작업 기록의 60~65%는 AI 스스로 코드 범위에 대한 거친 추정이라고 설명한 수치다. 실행으로 합격한 항목을 센 진행률로 사용할 수 없다.

**셋째, 구현과 피드백 사이의 간격이 길었다.** 실행 가능한 한 구간을 사용자가 확인한 뒤 넓히는 대신, 여러 기능을 추가한 뒤 원본과 조작이 다른 점을 다시 맞췄다. 최근에는 실행하지 않은 UI 수정 보고도 반복되었다. 매번 전체 검사를 할 필요는 없지만, 화면과 입력이 핵심인 작업에는 정기적인 실제 조작 확인이 필요하다.

**넷째, 원본과 포트가 함께 변했다.** 현재 웹 작업 트리에도 여러 미커밋 변경이 있다. 어느 시점의 원본을 옮기는지 고정하지 않으면 Godot이 따라가야 하는 기준도 계속 움직인다. 포팅 기준을 정하는 것은 원본의 변경을 버리거나 되돌리자는 뜻이 아니다.

Luna라는 모델 선택이 얼마나 영향을 줬는지는 이 기록만으로 분리해 측정할 수 없다. 더 강한 추론 모델을 설계 검토에 쓰는 것은 도움이 될 수 있지만, 모델만 바꾸고 같은 무기한 목표를 주면 범위 문제는 남는다. 준영이의 “구체적으로 미리 상의하라”는 조언은, 현재 설명에 따르면 작업 전에 목적·대안·검증 기준을 정하자는 뜻으로 받아들이는 것이 적절하다.

## 사용자 답변으로 정리된 방향

| 항목 | 현재 방향 |
|---|---|
| 개발 기반 | 앞으로 게임 엔진을 중심으로 개발하고 싶으며, Godot 전환을 목표로 유지한다. |
| 현재의 불편 | 브라우저별 환경과 설정 차이, 웹 기술로 게임 동작을 직접 구현하는 부담이다. 개별 문제의 원인은 실행 비교로 확인한다. |
| Electron의 위치 | PC 실행 대안은 될 수 있지만 게임 엔진으로 개발하고 싶다는 목적을 대신하지 않는다. |
| 준영이의 참여 | 직접 개발·유지보수할지는 아직 정해지지 않았다. 참여를 전제하거나 참여 여부 때문에 현재 계획 정리를 막지 않는다. |
| 최종 결과 | 현재 브라우저 버전의 게임이 Godot에서 정상적으로 돌아가고, 익숙한 화면과 조작을 유지한다. |

사용자가 전체 카드·적·저장 규칙을 다시 명세할 필요는 없다. 현재 원본 코드를 기준으로 AI가 이식·검증 목록을 만들고, 결과를 크게 바꾸는 모호한 부분만 질문한다. 원본과 거의 같은 UI를 요구한 기존 요청도 계속 유효하다.

**Godot 전환 방향은 유지하되, 지금까지의 끝없는 차이 찾기 방식으로 작업을 재개하지 않는다.** 기존 포트의 실행 상태와 남은 차이를 먼저 파악하고, 확인 가능한 작은 구간씩 끝낸다. 현재 코드를 버리거나 C#으로 재작성하는 결정은 하지 않는다.

## 최종 목표를 확인할 항목

아래는 사용자의 “현재 버전이 딱 잘 돌아간다”를 검증 가능한 항목으로 나눈 것이다. 이 표 자체가 구현 완료를 뜻하지는 않는다. 재개 전 현재 코드를 확인해 각 항목에 합격·실패·미확인 상태와 근거를 붙인다.

| 구간 | 확인할 결과 |
|---|---|
| 실행과 탐험 | 최신 소스로 화면이 뜨고 지도 이동·시야·적 조우·클릭 이동·자동 탐사가 원본의 관측 정보와 규칙을 따른다. |
| 전투 화면과 입력 | 손패·파일·적이 익숙한 배치로 보이며 카드 사용·드래그 이동·대상 선택·턴 종료를 원본처럼 조작할 수 있다. |
| 전투 규칙과 콘텐츠 | 합의한 현재 카드·적·스티커·에디션의 수치와 발동 순서가 원본과 일치한다. 기존에 합의한 포팅 제외 범위는 유지한다. |
| 보상과 덱 관리 | 전투 종료·보상·금고·인벤토리·덱 편집·스티커 서비스가 하나의 플레이 흐름으로 이어진다. |
| 저장과 복원 | 원본에 대응하는 탐험 진행을 저장·복원하고 새 탐험·패배 처리를 맞춘다. 기존 개발 저장의 이전은 필수 작업으로 추가하지 않는다. |
| 화면과 연출 | 대표 화면 크기에서 잘림·겹침·입력 방해가 없고, 원본의 주요 툴팁과 피드백이 동작한다. 작은 장식은 뒤에 맞추되 최종 범위에서 임의로 삭제하지 않는다. |
| 배포 | 개발 프로젝트 실행과 별도로 내보낸 Windows 빌드가 Godot 편집기 없이 실행된다. |

이식 기준은 현재 원본 작업 트리로 정하고, 시작 시 파일 상태를 기록해 비교 기준을 고정한다. 이후 추가되는 기획은 별도로 관리한다. 웹과 Godot에 새 기능을 계속 동시에 추가하는 작업까지 이번 이식에 섞지 않는다.

## 재개한다면 먼저 끝낼 작은 작업

첫 작업은 새 시제품을 처음부터 만드는 것이 아니라 **현재 Godot 코드로 대표 전투 한 개를 안정적으로 플레이할 수 있는지 확인하는 것**이다. 이미 있는 지도·전투·덱 편집을 살펴 최종 확인 항목의 상태를 먼저 기록한 뒤, 대표 전투에서 막히는 부분만 고친다. 전투 한 개는 전체 이식의 최종 목표를 축소하는 것이 아니라, 작업 방법과 검증 기준을 먼저 확립하기 위한 첫 단계다.

- 기준으로 삼을 웹 소스와 화면을 하나 정한다. 미커밋 변경도 포함해 현재 원본을 보존하고, 합의한 범위 밖 원본 변경은 별도 목록에 남긴다.
- 고정된 덱과 적으로 전투를 시작한다. 대표 카드에는 피해·방어·드로우·파일 이동이 포함되게 한다.
- 손패에서 적에게 카드 사용, 손패→파일, 파일→파일 이동, 잘못된 드롭 취소를 직접 확인한다.
- 턴 종료와 승리 후 보상·지도 복귀가 끊기지 않는지 확인한다.
- 같은 화면 크기에서 원본과 비교해 카드가 잘리거나 조작이 막히는지 확인한다. 작은 장식 차이는 다음 단계로 넘길 수 있다.
- 실패하면 해당 구간을 고치고 다시 확인한다. 합격한 뒤 전투→보상→지도 복귀→덱 편집으로 검증 범위를 넓히고, 나머지 콘텐츠와 예외 규칙을 확인한다.

화면을 수정할 때는 카드 같은 반복 부품과 화면별 책임을 나눠, 이후에도 Godot에서 다듬기 쉬운 구조를 지향한다. 현재 `main.gd` 전체를 한 번에 분해하는 별도 대공사로 확대하지 말고, 실제 수정하는 화면에서 필요한 부분부터 정리한다.

처음에는 합의한 짧은 작업 구간 하나, 예를 들어 60~90분으로 제한한다. 이는 전체 포팅의 일정 약속이 아니라 다음 판단을 위한 작업 상한이다. 시간이 끝나면 다음 세 가지를 남기고 멈춘다.

1. 실제로 확인한 동작과 확인 방법
2. 재현 가능한 남은 문제와 실행할 파일
3. 다음 한 작업의 범위, 예상되는 어려움, 계속할 가치가 있는 이유

진행 보고는 “65%” 대신 “대표 조작 6개 중 4개 합격, 1개 실패, 1개 미확인”처럼 분모가 있는 항목으로 한다. 규칙 이식은 같은 입력과 통제한 난수를 주었을 때 웹·Godot 결과가 맞는 대표 사례부터 비교한다. UI는 실제 화면과 입력을 확인하고, 배포가 목적이라면 내보낸 실행 파일의 실행도 별도로 확인한다. Godot 프로젝트 시작과 배포용 빌드는 다른 단계다. [Godot 내보내기 안내](https://docs.godotengine.org/en/stable/tutorials/export/exporting_projects.html)

## 다음 설계 검토에 사용할 요청문

> Ruinfall은 TypeScript·React 웹 게임이며 Electron 데스크톱 실행기도 있다. 사용자는 단순한 PC 실행 파일보다 앞으로 게임 엔진에서 개발하는 것을 원한다. 브라우저마다 환경과 설정이 달라지고 웹 기술로 게임 동작을 직접 구현하는 부담이 커 보여 Godot 전환을 선택했다. 목표는 현재 브라우저 버전의 게임이 Godot에서 정상적으로 돌아가며 익숙한 화면과 조작을 유지하는 것이다.
>
> Luna에 맡긴 작업은 약 40시간 이어졌고 지도·전투·덱 편집 등이 있지만, 실제 플레이의 합격 여부와 남은 작업을 명확히 관리하지 못했다. 이후 Sol이 현재 작업본과 GDScript를 유지하는 방향으로 첫 실행 구간에 착수했다. 최신 실행 상태는 체크리스트를 읽어 확인하라. 준영이의 직접 개발 참여는 정해지지 않았으므로 이를 전제하지 말라.
>
> 먼저 이 검토 문서, 원본 게임과 현재 Godot 코드를 읽고 설계만 검토해 달라. 코드 수정이나 포팅 재개는 하지 말라. 기존 변경은 보존하라.
>
> Godot을 주 개발 기반으로 삼으려는 목적을 존중하고, 이미 만든 포트를 활용할 진행 계획을 세워라. 기존 웹 코드를 기준으로 화면·조작·규칙·저장·배포 확인 목록을 직접 만들고, 각 항목의 구현 상태와 실제 검증 여부를 구분하라. 사용자에게 게임 전체를 다시 명세하도록 요구하지 말라. 기존 포팅 제외 합의와 미커밋 변경을 보존하라.
>
> 결과를 크게 바꾸는 모호한 부분만 질문하라. 대표 전투 하나의 실제 조작 확인을 첫 단계로 삼아 짧은 작업 범위·합격 조건·중단 시점·검증 방법을 제안하고, 그다음 전체 플레이 흐름과 콘텐츠 일치를 확인하는 순서를 정하라. 엔진의 제작 도구를 활용하기 쉬운 구조를 고려하되 전체 재작성이나 일괄 리팩터링부터 제안하지 말라. 근거 없는 전체 완료율이나 완료 날짜는 제시하지 말라. 계획을 검토한 뒤 구현 작업을 별도로 요청하겠다.

## 판단의 근거와 범위

- 현재 사용자 설명: Luna에 약 40시간 맡겼으며, 준영이는 작업을 구체적으로 미리 상의하라고 조언했다. 이후 사용자는 게임 엔진을 앞으로의 개발 기반으로 삼고 싶으며, 현재 브라우저 버전이 Godot에서 정상적으로 돌아가는 것이 목표라고 구체화했다.
- 「코드 변경」 채팅의 11월 10~12일 요청과 작업 보고: 초기 목적, 작은 시제품 제안, 전체 포팅 확대, UI 우선 요청, 실행 문제, 중단 보고를 확인했다. 과거 보고의 구현·검증 주장은 당시 보고로 취급한다.
- 검토 시점의 로컬 파일: [Godot README](../godot/README.md), [main.gd](../godot/scripts/main.gd), [battle_rules.gd](../godot/scripts/battle_rules.gd), [main.tscn](../godot/scenes/main.tscn), [desktop README](../desktop/README.md), [package.json](../package.json).
- 초기 검토는 코드와 기록을 읽고 작성했다. 이후 사용자 요청으로 시작한 실행·GUI 입력 검증의 최신 결과는 체크리스트에 따로 기록한다. 현재 포트의 모든 기능이 정상이라는 판정은 아니며, 전체 남은 시간이나 완료율도 새로 추정하지 않았다.

현재 작업본과 GDScript 유지 결정 및 첫 실행 작업은 사용자 요청에 따라 진행했다. 별도 엔진·언어 전환, 기존 코드 삭제, 커밋·푸시는 이 결정에 포함하지 않는다.
