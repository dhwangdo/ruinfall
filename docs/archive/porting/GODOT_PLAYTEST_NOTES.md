# Godot 플레이 메모

플레이하면서 발견한 불편함·버그·개선 아이디어를 모은다. 새 메모의 기본 상태는 **대기**다. 메모를 추가하는 것만으로 현재 작업을 중단하거나 즉시 수정을 시작하지 않는다. 후속 작업을 고를 때 중요도와 재현 여부를 보고 우선순위를 정한다.

## 남기는 방법

- 대화에 **“플레이 메모: …”**라고 말하면 이 문서에 대기 항목으로 기록한다.
- 이 파일에 직접 짧게 적어도 된다. 어느 화면에서 무엇이 불편했는지 한 줄이면 충분하다.
- 즉시 해결을 원할 때는 **“지금 고쳐줘”**라고 함께 말한다.
- 재현 순서, 기대한 모습, 캡처는 있으면 덧붙인다. 항목 번호와 분류는 나중에 정리해도 된다.

## 대기 중인 메모

### PT-001 방향키를 한 번 눌러도 여러 칸 이동함

- 접수: 2026-11-13 사용자 플레이 보고
- 상태: **플레이 확인 대기 · Luna 수정, Sol 검토 및 합성 입력 검사 완료**
- 화면/상황: 지도에서 방향키 입력
- 관찰: 한 번 눌러도 너무 길게 이동한다. 반복 입력 간격이 짧게 느껴진다.
- 후속 확인: 짧게 누름과 길게 누름을 구분해 이동 횟수, 최초 반복 지연, 반복 간격, 키를 뗀 뒤 정지 시점을 웹과 비교한다. 단일 입력에서 의도하지 않은 추가 이동이 생기는지 먼저 재현한다.
- 연결: 체크리스트 **D03 이동과 시야**
- 배정 범위: 지도 키 입력 한 건만 처리한다. 짧은 입력·길게 누름·키 해제·OS 반복 이벤트를 웹과 대조한다. 입력 구조 전반의 변경이나 두 번의 수정 실패가 필요하면 Sol에게 근거를 넘기고 멈춘다. PT-002·003은 대기로 유지한다.
- 확인한 원인: Godot은 키를 누르는 동안 `_process`에서 0.02초마다 이동을 반복하고 OS echo는 무시했다. 웹은 keydown 및 OS 반복 keydown을 20ms 타이머로 합쳐 처리하므로, 0.02초마다 독립적으로 반복하는 방식과 다르다.
- 수정: `godot/scripts/main.gd`의 별도 반복 타이머와 held 상태를 제거하고 지도 이동 키의 OS echo만 기존 한 칸 이동 경로로 보낸다. 다른 동작의 echo 차단과 모달 차단은 유지했다.
- 확인 범위: 합성 입력을 실제 `_unhandled_key_input` 처리 함수에 넣고 이동 실행 함수를 카운터로 대체했다. 단일 입력 1회, 두 echo 각각 1회, echo 사이/키 해제 뒤 추가 이동 0회, O키 echo 무시, 이름 입력창의 이동 차단을 확인했다. 실제 Windows 키 입력이나 전체 GUI 이벤트 전달 시험은 아니다.
- 남은 확인: 실제 키보드로 짧게 눌렀을 때 한 칸씩 움직이고, 길게 눌렀다 뗄 때 원하는 속도·정지감인지 사용자 플레이에서 확인한다. D03 전체와 동시 방향키 조합의 웹 20ms 합치기는 이번 완료 범위에 포함하지 않는다.
- 근거: [입력 검사 보고](../outputs/godot-validation/2026-11-12-ui/pt001-input-report.json), [실행 로그](../outputs/godot-validation/2026-11-12-ui/pt001-synthetic.log)

### PT-002 패배 후 다시 시작하기까지 오래 멈춤

- 접수: 2026-11-13 사용자 플레이 보고
- 상태: **로딩 안내·단일 worker 반영 · GUI/종료 경계 검사 완료 · 플레이 확인 대기**
- 화면/상황: 사망 후 다시 시작하는 흐름
- 관찰: 다시 시작할 때까지 게임이 오래 멈춘 것처럼 보인다. 웹에서는 지도를 불러오는 중이라는 로딩창을 보여줬다.
- 원인 측정: 격리한 현재 Godot 프로젝트에서 Godot 4.7.2 headless로 분리 측정했다. 패배 화면 뒤 `_start_run` 동기 구간은 5,559ms, 같은 시드로 `MapRules.create_map()`만 실행하면 5,512ms, 이미 생성된 지도에서 `_show_map()`만 다시 실행하면 5ms였다. 이번 측정에서는 지도 생성이 멈춤 시간 대부분을 차지했다. [측정 보고](../outputs/godot-validation/2026-11-13-ui/pt002-timing-luna/pt002-timing-report.json)
- 판정 한계: 화면 렌더나 실제 마우스 입력을 포함하지 않은 headless 측정이다. 브라우저 런타임과 비교하지 않았다. 사용자가 localhost 실행을 나중으로 미뤄 해당 비교는 보류한다.
- 후속 확인: 패배 → 재시작 입력 → 새 지도 표시의 어느 구간에서 얼마나 멈추는지 측정하고, 웹의 로딩 안내·진행 표시와 비교한다. 오래 걸리는 작업의 화면 피드백과 응답성을 함께 검토한다.
- Sol 1차 수정: `main.gd::_start_run()`이 먼저 “지도를 불러오는 중…”과 `지역 0 / 7`을 표시하고, 기존과 같은 순서로 지역을 생성하며 지역 사이에 두 UI 프레임을 양보했다. `map_rules.gd`의 초기 사전·지역 생성·마무리를 공유 함수로 분리했으며 기존 동기 `create_map()`도 같은 함수를 사용한다. 부분 지도는 로컬에 보관하고 완성 뒤에만 `run_state` 교체·저장을 하며, 로딩 중 저장과 중복 시작을 차단한다. 기존 저장이 있으면 로딩 중 그대로 두고 완성 후 대체하며, 패배에서는 기존처럼 삭제한다. 지역별 메인 스레드 생성은 아래 2차 worker 수정으로 대체됐다.
- Sol 확인: 격리 Godot 4.7.2 GUI probe **22/22**, 종료 코드 0. 첫 시작과 실제 재시작 버튼의 `Viewport.push_input` 클릭 뒤 모두 지역 0~7의 렌더 프레임을 확인했다. 재시작 callback은 1.002ms에 반환했고 지도 완료까지 5,851.768ms였다. 변경 전 생성기와 새 동기 API는 시드 `20261113`에서 전체 Variant 바이트가 같았으며, 비동기 시작의 시드 `2174650183` 지도도 변경 전 생성기와 전체 바이트가 같았다. 중복 시작 거부, 부분 저장 차단, 패배 저장 삭제, 완성 상태와 저장 일치, 저장 복원 시 재생성 없이 동일 지도 복원을 확인했다. [GUI 보고](../outputs/godot-validation/2026-11-13-ui/pt002-loading-sol/loading-report.json), [로딩 시작](../outputs/godot-validation/2026-11-13-ui/pt002-loading-sol/restart-step-0.png), [4지역 완료](../outputs/godot-validation/2026-11-13-ui/pt002-loading-sol/restart-step-4.png).
- 1차 한계: 총 생성 시간은 줄지 않았고 지역 내부 동기 계산으로 재시작 최대 프레임 간격 963.612ms, 첫 시작 1,014.985ms가 남았다. 이 결과로 아래 2차 작업을 진행했다. 1차 최종 검증 PID 33748은 정상 종료했다.
- 2차 단계 측정: 시드 `20261113`의 격리 headless 측정에서 총 9,174.957ms 중 바닥 생성은 지역당 631.724~1,130.603ms, 장소 배치는 178.956~265.402ms, 적이 있는 지역의 적 생성은 221.716~350.886ms였다. 단계 사이 yield만으로는 가장 긴 단일 바닥 생성 호출이 남으므로 전체 생성 순서를 그대로 단일 worker로 옮겼다. 서로 다른 실행의 총 시간은 직접적인 속도 비교로 사용하지 않는다. [단계 보고](../outputs/godot-validation/2026-11-13-ui/pt002-worker-sol/profile-report.json).
- 2차 수정: 새 `run_map_generation_job.gd`는 worker 하나에서 로컬 map만 만들고 완료 후 join으로 결과를 한 번 전달한다. 메인과 공유하는 취소/완료 지역 수는 mutex로 보호한다. 노드·UI·저장 접근은 메인에만 있으며, 로딩 문구의 점이 프레임마다 시간에 맞춰 바뀐다. 트리 이탈 시 취소하고 현재 지역이 끝나면 join하며, 시작 세대 번호로 join 뒤 UI 대기 중 이탈도 최종 상태 반영을 막는다. 메인 스레드의 씬 접근을 worker로 보내지 않는 [Godot 스레드 지침](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html)을 따른다.
- 2차 확인: 격리 Godot 4.7.2 GUI **27/27**, 별도 join 후 이탈·문구 애니메이션 **3/3**, 모두 종료 코드 0. 재시작 callback 1.783ms, 생성 완료 6,626.100ms, 최대 프레임 간격 **37.834ms**였고 첫 시작 최대 간격은 67.437ms였다. 시드 `1766371484` worker 지도와 변경 전 생성기, 고정 시드 `20261113` 동기 API와 변경 전 생성기가 전체 Variant 바이트에서 같았다. 기존 저장·재시작 검사도 통과했고, worker 실행 중 이탈과 join 직후/최종 저장 전 이탈 모두 저장·상태 반영 없이 끝났다. [worker 보고](../outputs/godot-validation/2026-11-13-ui/pt002-worker-sol/worker-report.json), [최종 반영 전 이탈 보고](../outputs/godot-validation/2026-11-13-ui/pt002-worker-sol/final-exit-report.json).
- 현재 한계: 총 생성 시간을 줄인 변경은 아니다. 로딩 중 프레임은 계속 진행하지만 **종료 시에는 현재 지역 완료까지 join 대기**가 남으며 실제 이탈 검사에서 1,073.965ms였다. 현재 worker는 순수 사전/배열 생성만 실행하므로 이후 생성 코드에 노드·리소스 변경을 추가할 때 이 경계를 유지해야 한다. 숨긴 GUI와 `Viewport.push_input` 검사이며 물리 입력 감각·브라우저 대조·사용자 플레이는 미확인이다. GUI PID 39944·40744는 정상 종료했고 인증서 저장소 환경 경고만 남았다. localhost·commit/push는 실행하지 않았다.
- 연결: 체크리스트 **H05 반복 플레이와 응답성**, **G03 저장 경계**

### PT-003 지도 맨 위에서 위쪽 타일이 보이지 않음

- 접수: 2026-11-13 사용자 플레이 보고
- 상태: **Godot 경계 표시 수정 · 격리 GUI 확인 완료 · 브라우저 비교/실제 플레이 확인 대기**
- 화면/상황: 지도의 가장 위쪽에 있을 때
- 관찰: 플레이어 위쪽 타일이 보이지 않는다. 타일이 있는데 가려진 것인지, 원래 없는 영역인지 사용자가 확신하지 못했다.
- 확인한 원인: 양 엔진의 시작 위치는 y=0이다. 웹 `getFixedRoomType()`은 y=-5~-1을 바위로 정의하고 `visibleMapRoomKeys()`는 벽을 통과하지 않는 시야를 계산한다. Godot `room_type_at()`도 걸을 수 없는 타일을 바위로 그리지만, `_reveal_visible()`이 y<0 전체를 제외해 첫 경계 타일을 `seen`에 넣지 않았다.
- 수정: Godot 시야 경계만 `-ROCK_BARRIER_HEIGHT`까지 허용했다. 바위는 여전히 걸을 수 없고, 기존처럼 벽 뒤쪽 행은 시야에 들어오지 않는다. 저장 형식·지도 생성·카메라는 바꾸지 않았다. 기존 탐험 복원도 현재 위치에서 `reveal_visible()`을 호출해 새 경계 표시를 반영한다.
- 확인: 격리 Godot 4.7.2 GUI probe **6/6**. y=-1의 바위형·비보행·발견/현재 시야와 실제 `MapView` 픽셀을 확인했고, y=-2는 벽 뒤라 가려지는지 확인했다. [probe 보고](../outputs/godot-validation/2026-11-13-ui/pt003-top-boundary-luna/godot/pt003-top-boundary-report.json), [캡처](../outputs/godot-validation/2026-11-13-ui/pt003-top-boundary-luna/godot/pt003-top-boundary.png)
- 남은 확인: 같은 상태의 브라우저 렌더와 실제 플레이는 보류다. 사용자가 localhost 실행을 나중으로 미뤘다.
- 연결: 체크리스트 **C04 지도 배치**, **D01 지형 생성**, **D03 이동과 시야**

## 처리 기준

- 메모의 등록 순서는 작업 우선순위가 아니다. 사용자가 순서를 지정하지 않았다면 전체 포팅의 선행 조건, 플레이에 미치는 영향, 다른 항목에도 도움이 되는 정도와 Luna가 맡을 수 있는 범위를 보고 Sol이 다음 일을 고른다.
- 새 사용자 메모를 자동으로 다음 작업에 배정하지 않는다. 사용자 플레이 확인을 기다리는 동안에도 독립적인 다른 포팅 작업은 진행할 수 있다.
- 상태는 대기 → 작업 중 → 확인 대기 → 완료로 기록한다. 보류할 때는 이유를 남긴다.
- 웹에도 있는 문제인지, Godot 포팅 차이인지, 새 개선 요청인지는 확인하며 분류한다.
- 수정 완료 시 관련 코드·검증 결과 또는 사용자 플레이 확인을 연결한다.
- 전체 포팅의 완료 조건과 진행 현황은 [포팅 체크리스트](GODOT_PORT_CHECKLIST.md)를 따른다.
