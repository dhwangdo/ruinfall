- [x] **S05 작업본과 언어:** 현재 Godot 작업본을 활용하고 GDScript를 유지한다. 첫 실행에서 수정 가능한 구체적 오류와 동작하는 화면을 확인했다. C# 전환이나 새 프로젝트 재작성은 이번 작업에 포함하지 않는다. 판단 근거는 포팅 검토 문서에 기록했다.

체크박스는 **해당 항목의 완료 조건을 검증했을 때만** 채운다. 코드나 문서에 구현이 있다고 적힌 것만으로 완료 처리하지 않는다. 기능 항목은 처음에 모두 미확인으로 두었고, 이후 실행 기록에 근거해 완료 표시를 갱신한다. 미확인은 새로 만들어야 한다는 뜻이 아니다.

| 상태 | 의미 |
|---|---|
| 미확인 | 현재 기준본에서 아직 해당 확인을 하지 않았다. |
| 진행 | 현재 작업 중인 항목이다. 한 번에 작은 범위로 제한한다. |
| 수정 필요 | 실패를 재현했으며 재현 순서와 기대·실제 결과를 기록했다. |
| 완료 | 항목에 적힌 조건을 확인했고, 방법과 결과를 남겼다. |

규칙은 웹의 현재 코드가 기준이다. 문서·과거 보고·테스트 기대값과 다르면 실행 경로를 확인해 코드를 따른다. 콘텐츠 수, 금고 홀드 시간처럼 문서별 값이 다른 항목도 코드로 확정한다.

## Sol과 Luna의 역할과 작업 전달

**첫 실행 구간 A·B는 Sol이 직접 맡고, 이후 범위와 완료 조건이 명확한 일을 Luna에 배정하는 방식을 권한다.** Sol은 계획만 작성하는 역할에 머무르지 않고 원인 추적·핵심 수정·검증·최종 판정까지 맡는다. Luna에 전체 포팅의 다음 일을 계속 스스로 고르도록 맡기는 방식으로 재개하지 않는다.

공식 OpenAI 안내는 판단이 필요한 복잡한 작업에 Sol을, 범위가 분명하고 반복 가능한 작업에 Luna를 쓰는 구분을 제공한다. 아래 분담은 이 안내와 현재 코드 구조를 바탕으로 한 프로젝트 운영 제안이며, 이 프로젝트에서 두 모델의 소요 시간이나 비용을 비교 측정한 결과는 아니다. [모델 선택 안내](https://developers.openai.com/api/docs/guides/model-selection), [Codex 모델 안내](https://learn.chatgpt.com/docs/models)

| 담당 | 맡을 일 | 결과물 |
|---|---|---|
| Sol | A·B 첫 실행, 화면·입력·규칙이 얽힌 오류 추적, 상태/저장/턴 순서/구조 판단, 작업 배정과 검토 | 재현 가능한 실행 상태, 필요한 수정, 검증 결과, 다음 작은 작업 |
| Luna | 기본 데이터 대응표, 확정된 규칙의 반복 적용, 원인이 좁혀진 작은 오류, 기준 화면과 수치가 주어진 독립 UI 부품 수정 | 지정한 범위의 표 또는 변경과 해당 검증 결과 |
| 사용자 | 짧은 플레이에서 원본과 조작감이 같은지, 눈에 띄는 차이가 있는지 판단 | 게임 기준의 피드백. 기술 항목 재명세나 매번의 작업 분배는 요구하지 않는다. |

게임 규칙이나 구조의 의미가 불명확한 수정은 Sol이 먼저 좁힌다. UI 작업도 원본과 비교할 결과가 명확하면 Luna에 맡길 수 있다. 모델 이름만으로 일을 나누지 않는다.

### 처음 세 번의 결과물

1. **Sol의 현재 상태 확인:** A01~A05에서 비교 기준과 실행 경로를 정리하고 지도·전투가 실제로 뜨는지 확인한다. 우선 지도·전투의 원본 화면을 남기고, 나머지 화면은 해당 영역에 착수할 때 기록한다. 전체 카드 재대조나 파일 전체 리팩터링은 시작하지 않는다.
2. **Sol의 대표 전투:** B01~B07을 실행하며 실패한 부분만 고친다. 결과물은 같은 덱·적·입력으로 다시 확인할 수 있는 전투와, 항목별 합격/실패 근거다. 여러 문제가 나오면 시작·조작·턴·승리 순으로 해결한다.
3. **Luna의 작은 시험 작업과 Sol 검토:** F01 카드 기본 데이터 88장, 일반 보상 풀 분류, 토큰 비용 표기를 대조했다. 흙·유독성 점액의 Godot 비용 필드를 제거해 웹의 비용 없음 표시와 맞췄다. `fourHit`/`five_hit`은 키만 다르고 소스상 모두 5회 공격한다. 특별·희귀 풀은 원소와 확률 분포가 같고 배열 순서는 다르다. 1지역은 단독 6·혼합 20·보스 1개 조우 27/27, 2지역은 단독 7·혼합 30·보스 1개 조우 38/38, 3지역은 일반 4·보스 1개 조우 5/5가 구성 순서와 체력 범위에서 일치했다. 미라 사제 행동·의도 순환 6/6, 미라 전사 행동·턴 시작 힘·순환 7/7이 소스 기준으로 일치했다. [카드 보고](GODOT_LUNA_F01_CARD_DATA.md), [지역별 적 보고](GODOT_LUNA_F01_REGION_ONE_ENEMIES.md), [미라 사제](GODOT_LUNA_F01_MUMMY_PRIEST_ACTIONS.md), [미라 전사](GODOT_LUNA_F01_MUMMY_WARRIOR_ACTIONS.md). 카드·적 효과의 실제 실행, 스티커·에디션은 미확인이다.

첫 Luna 작업은 전체 F01이나 F06의 완료가 아니다. F06 같은 큰 체크리스트 항목은 효과 종류나 재현 사례로 더 나눠 배정한다. 이후 UI 우선순위에 따라 C를 진행하며 데이터 대조 결과는 F에서 활용한다.

### 한 번 배정할 작업의 내용

Luna에 일을 넘기기 전에 Sol이 다음 내용을 채운다. 실제 문제가 확인되기 전에는 수정 대상과 원인을 추측해 확정하지 않는다.

| 필드 | 전달할 내용 |
|---|---|
| 연결 항목 | 체크리스트 ID와 이번에 처리할 부분 한 개 |
| 문제와 목표 | 재현한 현재 결과와 원본에서 확인한 기대 결과. 자료 정리 작업이면 추출할 필드와 포함 범위 |
| 기준 자료 | 현재 기준본, 관련 파일·함수, 필요하면 시드·덱·적·화면 크기·스크린샷 |
| 변경 범위 | 수정할 파일과 책임 범위. 규칙·UI·저장을 함께 바꿔야 하면 Sol이 먼저 설계를 좁힘 |
| 완료 조건 | 수행할 검사나 실제 조작과 성공 판정 |
| 보고 | 바꾼 내용, 실제 확인한 방법과 결과, 미확인 사항, 다음 작업이 필요한 이유 |
| 종료 시점 | 해당 결과물을 제출하고 종료. 새 기능이나 다음 체크리스트 항목을 임의로 시작하지 않음 |

처음에는 한 작업을 대략 20~30분 안에 결과나 구체적인 장애를 보고할 수 있는 크기로 자른다. 이는 완료 시간 보장이 아니라 범위와 진행을 점검하는 간격이다. 같은 문제에 대한 수정 시도 두 번이 실패하거나, 허용 범위 밖 상태·저장·규칙 변경이 필요해지면 근거를 남기고 Sol이 재검토한다. 사용자에게 일상적인 기술 판단을 되묻는 단계로 만들지 않는다.

### 변경 충돌과 검토

- 현재 원본 작업공간을 사용한다. 별도 worktree에 최신 미커밋 변경이 있다고 가정하지 않는다.
- 동시에 수정하는 작업자는 처음에는 한 명으로 제한한다. 특히 `main.gd`는 Sol이 기본 담당하고, 일부 수정을 Luna에 맡기면 해당 작업 동안 Sol은 그 파일을 수정하지 않는다.
- 독립된 읽기 전용 자료 정리는 병행 후보가 될 수 있지만, 실제 배정은 별도로 정한다. 기존의 중단된 전체 포팅 작업을 그대로 재개하지 않는다.
- Sol은 전달된 요약만으로 완료를 승인하지 않고 변경 내용과 관련 실행 경로를 검토한다. 코드 대조·규칙 검사·실제 화면/입력 확인을 구분한다. UI를 직접 확인할 수 없으면 사용자 확인이 필요한 정확한 조작을 남기고 검증 완료로 표시하지 않는다.
- Luna의 생성 속도만 비교하지 않는다. 검토와 수정까지 포함해 이 방식이 유용한지 보고, 재작업이 많으면 그 종류의 일은 Sol이 직접 수행한다.
- 전체 일정·모든 버그·모든 수정 파일을 지금 확정하지 않는다. 작업 순서·담당 기준·완료 판정·막혔을 때의 처리부터 정하고, 실제 실행에서 찾은 문제를 다음 작업으로 구체화한다.

- [x] **A03 최신 프로젝트 실행:** 원본 작업공간의 현재 Godot 소스를 실행하고 실제 지도까지 확인한다. 런처가 선택하는 엔진·프로젝트와 직접 실행 경로를 대응시키고, 기존 창과 오래된 내보내기 EXE를 구분하며 경로·Godot 버전을 남긴다.

- [x] **A05 현재 작업 목록 확정:** 위 기존 작업물 표를 바탕으로 분야별 구현 위치와 아직 확인하지 못한 부분을 기록한다. 이미 증거가 있는 항목만 결과를 붙이고 나머지는 미확인으로 둔다. 이후 항목별로 추가 구현·수정·검증을 구분하며, 이 준비 단계에서 전체 규칙을 다시 전수 대조하지 않는다.

## B 먼저 합격시킬 대표 전투

고정된 시작 상태로 기본 피해·방어·드로우·솔리테어 이동을 확인할 수 있는 덱과 일반 적 한 종류를 고른다. 선택한 카드·적·초기 상태를 기록해 같은 상황을 다시 만들 수 있게 한다. 이 대표 전투가 합격하면 기존 구현을 이용해 나머지 플레이 흐름으로 넓힌다.

- [x] **B01 진입과 초기 배치:** 지도 조우 → 필요한 경우 전투 전 덱 확인 → 전투 시작이 이어진다. 시작 덱·파일 배치·첫 드로우·체력·에너지·별이 기준 상태와 맞는다. 복수 보유 덱 선택과 현재 소스의 초기 배치 비교를 확인했다.
- [x] **B02 대상 카드 사용:** 손패의 단일 대상 카드를 적에게 드래그하거나 선택 후 적을 클릭해 사용한다. 잘못된 곳에 놓으면 원래 자리로 돌아오고 비용·카드가 소모되지 않는다. 중앙에 놓거나 더블클릭했다는 이유로 첫 적이 자동 지정되지 않는다. 이번 확인은 드래그 경로이며 클릭·더블클릭 경로는 C03에서 확인한다.
- [x] **B03 자신·전체 효과 사용:** 방어·드로우·전체 공격 등 중앙에서 사용할 수 있는 카드가 정상 작동한다. 대상 판정에 맞는 곳만 강조되며 드로우가 파일 선택을 요구하면 그 선택까지 이어진다. 방어·전략가·휩쓸기의 대표 경로이며 모든 카드 효과는 F06에 남긴다.
- [x] **B04 솔리테어 이동:** 손패→파일, 파일→파일 이동과 연속 묶음 이동을 확인한다. 배치 가능 여부와 별 소모가 맞고, 별 부족·자기 파일·잘못된 조합은 거절한다. 웹 규칙과의 고정 상태 비교 및 실제 Godot GUI 입력으로 확인했으며 아래 후속 기록을 따른다.
- [x] **B05 턴 종료와 다음 턴:** 남은 손패 처리 → 적 행동 → 방어·에너지·다음 드로우가 순서대로 진행된다. 연타·드래그 중 종료로 턴이 중복 처리되거나 입력이 영구 잠기지 않는다. 전환 중 다른 행동 거절·다음 턴 드래그 재개·초기화 후 오래된 처리 취소를 확인했다.
- [x] **B06 승리와 복귀:** 적 처치 → 승리 표시 → 보상 확정 → 복귀 버튼 → 지도 복귀가 이어진다. 일반전 열쇠와 카드 보상은 해당 타일에 한 번만 지급된다. 준비한 승리 경계와 B07 연속 전투에서 확인했으며, 보스·미래 지역 적의 덱 보상은 E02에서 확인한다.
- [x] **B07 대표 전투 합격 기록:** 같은 사례를 수정 후 다시 실행해 결과를 남긴다. 시작 로그만 정상인 상태를 합격으로 처리하지 않는다. 막힌 조작이 없음을 실제 입력으로 확인한다. 시작 덱 20장과 진흙 인형의 고정 시작 상태를 두 번 실행해 행동·결과 기록이 일치했다.

## C 주요 화면과 조작

사용자 우선순위에 따라 기본 배치와 드래그 조작을 먼저 맞춘다. 최종 화면 마무리는 H에서 다시 확인한다.

- [ ] **C01 공통 카드:** 전투·덱 편집·바닥·검색·보상·미리보기에서 이름·비용·효과·희귀도·스티커·묶음 수와 글꼴이 원본처럼 표시된다. 웹과 Godot에서 실제 선택된 글꼴 및 한글 폴백을 비교한다. 카드마다 별도의 외형을 중복 구현해 수정 결과가 어긋나지 않게 한다. 공유 카드 위젯의 제목·본문·강조, 덱 편집·검색 결과 작은 카드의 이름, 작은 미리보기의 이름·설명은 웹의 Pretendard 파일을 사용한다. 전투 설명 86개를 다시 확인했다. 다른 별도 카드 화면과 실제 글리프 폴백은 미확인이라 C01은 미완료다(아래 Luna/Sol C01 기록).
- [ ] **C02 전투 배치:** 플레이어 왼쪽, 파일 가운데, 적 오른쪽, 손패 하단의 원본 배치를 맞춘다. 손패 부채꼴·가로 넘김, 파일 스택·가로 넘김, 턴 종료 버튼 접근성을 실제로 확인한다.
- [x] **C03 카드 선택과 보조 입력:** 더블클릭·대상 선택, 숫자키 선택·전환, Escape/우클릭 키보드 드래그 취소, Space 정렬, E 턴 종료, 강제 버리기 중 클릭·숫자·Enter 입력을 실제 Windows PC GUI에서 확인했다. 상세 결과와 한계는 아래 실행 기록을 따른다. 모바일 단일 클릭 선택은 범위 밖이다.
- [ ] **C04 지도 배치:** 지도·상단 정보·현재 위치·적·바닥 물품·골드·금고·포탈·핑의 표시가 원본과 대응한다. 카메라 드래그와 확대·축소가 타일 클릭·물품 획득을 잘못 실행하지 않는다.
- [ ] **C05 덱 편집 배치:** 원본의 인벤토리·보유 덱·현재 바닥 배치와 스크롤·카드 크기를 맞춘다. 실제 원본 화면과 비교하며, 드래그할 수 있는 곳을 별도 이동 버튼으로 대체하지 않는다. 1280×820에서 패널 너비와 바닥 행 위치를 웹에 가깝게 조정했지만 상단·인벤토리·덱 행과 세부 외형은 미완료다.
- [ ] **C06 장소와 검색 화면:** 금고·제단·땜장이·변환기·검색·설정의 주요 배치, 결과 미리보기, 닫기·Esc·창 밖 클릭을 맞춘다. 창이 열린 동안 뒤쪽 지도 입력이 실행되지 않는다.
- [ ] **C07 설명과 수치:** 카드·적 의도·상태·스티커·에디션 툴팁이 올바른 대상과 현재 수치를 설명한다. 호버에서 드래그·스크롤·화면 전환으로 넘어가도 설명창이 남아 입력을 가리지 않는다. 지도 검색의 실제 호버·스크롤·Esc/바깥 클릭은 Sol GUI 17/17로 확인했다. 나머지 툴팁·화면 전환과 물리 입력은 미확인이다([부분 기록](GODOT_LUNA_C07_MAP_SEARCH_PREVIEW.md)).

## D 지도와 탐험 규칙

웹 기준 위치: `app/game/map*.ts`, `app/hooks/useRunMapContent.ts`, 지도 입력 훅과 장소 컨트롤러. Godot 후보 위치: `map_rules.gd`, `map_generation_rules.gd`, `map_travel.gd`, `map_enemies.gd`, `map_view.gd`와 `main.gd`.

- [ ] **D01 지형 생성:** 7개 지역의 크기·경계·안전구역·수제 금고 지형·연결 통로를 대조한다. 고정한 여러 시드의 1·2·3·7지역에서 지형과 필수 장소 도달 가능성을 확인한다. 기존 시드 비교 보고는 기준본에서 재현한다.
- [ ] **D02 콘텐츠 배치:** 금고·포탈·서비스·골드·일반 적의 수·위치·지역별 풀·분산 규칙을 확인한다. 상점·축복·바닥 카드·티켓 등 자연 생성하지 않는 요소가 새로 나타나지 않는다. 4~7지역에 원본에 없는 적·보스를 추가하지 않는다.

- [ ] **D04 적 행동과 조우:** 거리장을 이용한 감지, 수면→깨어남→경계, 배회·추적, 보스 고정, 미래 지역 적의 영구 수면을 확인한다. 적 또는 플레이어가 같은 칸에 들어가면 전투가 시작되고 시야 밖 실제 위치는 화면·경로 판단에 새지 않는다.
- [ ] **D05 클릭 이동:** 알려진 지형·관측한 적을 바탕으로 원본의 안전도·길이·회전 우선순위로 이동한다. 새 적 발견·실제 충돌·취소 시 올바르게 멈추고 더블클릭 핑 해제가 이동으로 번지지 않는다.
- [ ] **D06 O 자동 탐사:** 안전한 미탐사 경계와 알려진 골드 수집, 목표·남은 경로 유지, 조사 완료 지점, 관측한 적 기억을 확인한다. 새 장소·위험·완료의 정지 이유가 맞고 왕복·무한 탐사·미발견 정보 조회가 없다.
- [ ] **D07 포탈과 안전구역:** 지역 포탈→안전구역→다음 지역 이동, 열쇠 소멸 경고·취소·이번 런 경고 생략, 회복 지형, 보스, 덱 편집 허용을 확인한다. 신들의 비탄과 카르마의 충전·초기화 시점도 맞춘다.
- [ ] **D08 미니맵과 검색:** 발견한 칸만 표시·검색하고 미개방 금고/개방 완료 금고를 구분한다. 필터·검색어·희귀도 정렬·상세 지도·핑·화면 밖 화살표·미니맵 이동/확대/크기 변경·플레이어 표식이 원본처럼 작동한다.

## E 보상과 덱 관리와 장소

웹 기준 위치: `rewards.ts`, 덱 생성 규칙, `deckEditorRules.ts`, `stickerServices.ts`와 티켓 관련 컨트롤러. 현재 실행 경로는 항목 착수 시 확인한다. Godot 후보 위치: `main.gd`, `card_catalog.gd`, `deck_editions.gd`, `deck_editor_rules.gd`, `stickers.gd`, `sticker_services.gd`.

- [ ] **E01 시작 상태:** 체력·빈 인벤토리·보유 덱 상한·시작 덱 20장·용량 25·희귀 슬롯 1·시작 스티커/에디션 없음이 원본과 맞는다. 카드·덱·물품의 식별자가 생성과 이동에서 겹치지 않는다.
- [ ] **E02 전투 보상:** 일반전·미래 지역 적·보스의 카드/덱·열쇠·스티커 지급과 희귀 누적 확률을 확인한다. 다수전·소환 적을 중복 전투로 세지 않고 골드·티켓을 전투 보상으로 추가하지 않는다.
- [ ] **E03 발견 덱:** 지역별 용량·희귀 슬롯·빈칸·카드 풀·에디션 예산·가중 추첨·이름·생성값 기록을 대조한다. 미리보기·재방문·복원으로 덱 내용이 다시 추첨되지 않는다.
- [ ] **E04 금고 개방:** 원본의 홀드 시간·입력·중도 취소·열쇠 부족·비용 지불을 확인한다. 성공하면 덱과 추출 티켓 1개를 한 번만 바닥에 지급하고 재개방되지 않는다.
- [ ] **E05 줍기와 바닥 배치:** 카드·덱·티켓의 줍기/놓기/직접 덱에 넣기, 인벤토리 포화, 빈 덱 슬롯, 덱 교체·정렬을 확인한다. 실패·취소·연타로 물품이 복제되거나 사라지지 않는다.
- [ ] **E06 덱 편집 이동:** 인벤토리↔덱↔바닥과 덱↔덱 드래그를 확인한다. 안전구역 안팎의 원래 소속·제거 예약·복원·희귀 카드 반환·용량/희귀 슬롯 제한·편집 종료 시 반영이 맞는다.
- [ ] **E07 티켓과 카드 팩:** 활성 티켓 각각의 사용 조건·선택·취소·소모·결과를 확인한다. 바닥 추출 티켓, 원래 덱 카드 제한, 포화 시 바닥 지급도 포함한다. 카드 팩은 티켓과 구분하며 자연 획득 경로가 없는 기능에 새 경로를 만들지 않는다.
- [ ] **E08 제단과 땜장이:** 제물/숙주를 어느 순서로든 드래그하고 유효한 조합만 받는다. 일반 카드/DIY 스티커 상한·중복·부적합 조합·가격·성공 횟수 증가와 카드 소속 보존을 확인한다.
- [ ] **E09 변환기와 거래 확정:** 같은 희귀도의 다른 카드와 유효한 스티커 교체, 0.1초 예시, 확정 시 실제 추첨을 대조한다. 세 서비스 모두 취소/비용 부족은 상태를 바꾸지 않고 연타는 중복 결제하지 않는다.

### B04 묶음 이동 후속 기록

2026-11-12 사용자가 Sol의 계속 작업을 요청했다. Luna에 배정하지 않고 같은 작업본과 GDScript로 진행했다.

- `solitaire_rules.gd`가 출발 카드·묶음 ID, 앞면 여부, 목적지, 별, 카드 효과 선택 대기와 배치 가능 여부를 판단한다. 화면의 드롭 강조와 실제 이동이 같은 검사를 사용한다.
- 파일의 노출된 앞면 카드를 잡으면 해당 카드부터 맨 위까지 순서를 유지해 옮긴다. 묶음의 별 비용은 잡은 카드 기준으로 한 번만 지불하며, 파랑새도 같은 기준이다. 묶음 안의 뒷면은 그대로 보존하고 새로 드러난 출발지 맨 위만 공개한다.
- 묶음 각 카드의 재련은 **이동 전 목적지 카드와 할인 상태**를 기준으로 평가한다. 여러 흑요석 단검이 대상 한 장을 중복 제거하지 않고, 치환 합금·금속학 연구·망치질 에디션과 손패 태엽장치의 기존 효과도 유지한다.
- 자기 파일·별 부족·뒷면 출발·잘못된 배치와 드래그 도중 카드 구성이 바뀐 오래된 입력은 카드와 자원을 바꾸지 않는다.
- 웹의 `top/bottom/spell` 판정 함수는 연결했지만, 현재 웹 획득 카드 목록에 이 필드를 쓰는 카드는 없다. 이 조건의 검사는 해당 필드를 넣은 검증 상태로 수행했으며, 카드 목록에 새 규칙을 추가하지 않았다. 주문 연쇄 같은 나머지 효과의 전체 검증은 F03에 남긴다.

[자동 비교 검사](../tests/godot-solitaire.test.mjs)는 현재 웹 `createMoveCardToPile`을 직접 실행한 결과를 실제 Godot 규칙 실행과 대조한다. 웹 비교 34사례와 추가 입력 거절 6사례가 통과했다. 일반·무료 이동, 묶음 순서, 복수 재련·교환·대상 소모·회수, 대기 상태와 오래된 입력을 확인하며 원본 상태를 변경하지 않는지도 검사한다. 실행 명령과 엔진 선택은 Godot README에 기록했다. 검사 파일 ESLint도 통과했다.

### B01·B03·B05·B07 대표 전투 후속 기록

2026-11-12 Sol이 같은 작업본에서 진행했다. [수정 전 실행](../outputs/godot-validation/2026-11-12-b07/before/report.json)에서 단일 적 조우가 기본 주황 슬라임으로 바뀌고 신들의 비탄 체력 감소도 빠지는 문제, 빠른 두 번의 턴 종료가 두 턴을 진행하는 문제를 재현했다.

단일 적은 카탈로그에서 적 딕셔너리 하나로 반환되는데 기존 시작 경로가 `enemies` 배열만 읽어 빈 목록을 넘기고 있었다. `battle_setup.gd`에서 단일·복수 조우를 같은 형태로 정리하고 카르마·비탄을 적용하도록 했다. 비탄은 웹 코드처럼 **현재 체력만** 70%로 줄이고 최대 체력은 유지한다. 충전은 조우당 한 번 차감한다.

턴 종료는 하나의 입력 단계로 묶었다. 0.3초의 전환 동안 버튼·카드 사용·파일 선택·정렬·대상 변경을 막고, 진행 중 드래그를 취소한 뒤 다음 턴에 입력을 연다. 새 탐험이나 새 전투가 시작되면 이전 전환 결과가 적용되지 않는다. 이 짧은 전환은 H02의 전체 전투 연출 완료를 뜻하지 않는다.

### Luna C05 후속: 작은 카드 기본 스타일 반영 (당시 렌더 미확인)

`godot/scripts/main.gd::_deck_editor_card_widget()`에 웹 `app/styles/item-visuals.css`의 기준을 반영했다: 기본 테두리 `#9a9da2`·4px, 희귀 테두리 `#d5a928`, 상단 띠 19.6px, 비용 Arial 16px, 카드명 Pretendard 강조 글꼴 13px, 스티커 25×25px. 중복 수 배지는 카드 전용으로 분리해 소모품의 기존 공용 배지는 유지했다. 이 기본 스타일 작업 당시에는 카드 스택 레이어를 구현하지 않았으며, 이후 아래 Sol C05 후속에서 구현하고 Godot GUI 렌더를 확인했다.

이 기본 스타일 작업 단계에서는 코드만 반영하고 Godot 렌더 캡처·GUI 확인은 하지 않았다. 이후 Sol 후속의 렌더·입력 확인 결과는 아래 기록을 따른다. 글꼴 실제 모양, 줄임표, 배지 위치·크기, 전체 카드 외곽선의 웹 화면과의 시각 대조는 남아 있다. C05 체크는 완료로 바꾸지 않는다.

2026-11-13 후속으로 Godot 공용 헤더 스타일과 웹 compact-card 색을 대조해 차이를 확인했다. 전설 작은 카드 헤더와 스택 띠는 웹 `#d5a928`을 사용하도록 작은 카드 전용 스타일 함수를 적용했다. 전체 전투 카드의 공용 헤더 색은 바꾸지 않았다. 격리 Godot 4.7.2 GUI 캡처에서 전설 카드와 뒷면 띠에 색이 적용된 것을 확인했다. 같은 상태의 웹 렌더 대조는 남아 있다.

긴 카드 이름은 웹 `text-overflow: ellipsis`처럼 말줄임표를 보이도록 compact Label에 `TextServer.OVERRUN_TRIM_ELLIPSIS_FORCE`를 설정했다. 웹과 Godot은 SHA-256이 같은 Pretendard WOFF2 파일을 사용한다. 웹 CSS의 600 weight·13.2px·-0.65px 자간·좌우 6px padding에 대응해, Godot 이름 Label은 600 weight·13px·-1px glyph spacing의 전용 FontVariation을 사용하고 MarginContainer의 좌우 10px로 62px 텍스트 폭을 만들었다(4px 카드 테두리 포함). 긴 한국어 이름 캡처와 텍스트 폭, 기존 카드 겹침·드래그 입력을 확인해 격리 Godot 4.7.2 probe **21/21** 통과했다([보고](../outputs/godot-validation/2026-11-13-ui/c05-card-name-luna/card-name-report.json), [캡처](../outputs/godot-validation/2026-11-13-ui/c05-card-name-luna/long-card-name-ellipsis-1280.png)). Godot의 정수 픽셀 제약 때문에 13.2px/-0.65px CSS 값과는 근사치다. 같은 상태의 웹/Godot 시각 대조와 이름 수직 위치·배지 크기/위치는 남아 있다.
